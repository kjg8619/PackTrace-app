# PackTrace — 팩 포장 아트 (PACK-ART-V1)

> 공개판 안내: 원 저장소의 검증 기록이다. 공개판에는 카드 카탈로그 스냅샷(`catalog-manifest.json`과 `scripts/prepare-catalogs.sh`로 설치)과 포장 그림 레지스트리 항목(출판사 그림, 재배포하지 않음)이 들어 있지 않다.

기준일: 2026-09-23 · 대상: `tpcgi-en-sv01-booster` · `tpcgi-en-sv02-booster` · `tpcgi-en-sv03-booster`
이 문서는 **실제로 확보·설치한 이미지**와 **확인하지 못한 것**을 구분해 적는다.
이미지 파일은 로컬 자산이며 Git에 넣지 않는다. 이 문서와 레지스트리 JSON만 저장소에 남는다.

## 0. 무엇을 그리는가

| 항목 | 값 |
|---|---|
| 상품 | Pokémon TCG: Scarlet & Violet 계열 **Sleeved Booster Pack (10 Cards)** — sv01/sv02/sv03, 영문판 |
| 개봉 연출이 표현하는 것 | 슬리브 **안쪽의 은박 부스터** 정면 (실제로 뜯는 대상) |
| 왜 슬리브 사진을 쓰지 않는가 | 연출은 은박 봉투를 찢는 장면이다. 종이 슬리브를 은박 팩처럼 찢으면 실제 상품과 다른 물체를 보여주게 된다 |
| 등록한 그림 수 | **3종 / 상품당 1장** (V1 범위) |
| 등록하지 않은 것 | 같은 세트의 다른 부스터 아트 변형, 팩 뒷면, 박스·슬리브·덱·프로모 이미지 |

세트별로 실제 부스터 아트 변형이 여러 개 존재한다(sv01 4종, sv02 5종, sv03 4종). V1은 **한 상품당 한 장**만
등록했고, 나머지 변형은 등록하지 않았다. 포장 그림을 여러 종류로 뽑는 기능은 v0.2 이후 범위다.

## 1. 레지스트리

| 항목 | 값 |
|---|---|
| 파일 | `Sources/PackTraceCore/Resources/pack-artwork/pack-artwork-v1.json` (커밋 대상, 바이너리 없음) |
| 타입 | `PackArtworkRegistry` / `PackArtworkDescriptor` / `PackArtworkResolver` |
| 매칭 키 | `productID` + `setID` + `language` **셋 다 일치**해야 적용 |
| 설치 위치 | `<데이터 루트>/pack-artwork/` (예: `~/Library/Application Support/PackTrace/pack-artwork/`) |
| Git | `.gitignore`의 `pack-artwork/` — 이미지 파일은 추적하지 않는다 |
| 카드 카탈로그 | **변경 없음**. 포장 아트는 표현용 자산이며 `catalogVersion`·`contentHash`·`recipeVersion`·pool·가격에 관여하지 않는다 |

## 2. 설치·검사 명령

```text
./scripts/fetch-pack-artwork.sh                 # 내려받기 → 검사 → 정규화 → 설치 (네트워크 사용)
./scripts/fetch-pack-artwork.sh --write-manifest # 위 작업 + 레지스트리의 정규화 해시 갱신
./scripts/fetch-pack-artwork.sh verify          # 설치된 파일을 레지스트리와 대조 (네트워크 없음)
./scripts/fetch-pack-artwork.sh list            # 등록된 항목 목록
```

- 앱 빌드·실행·개봉은 **이미지를 내려받지 않는다.** 설치된 파일을 읽기만 한다.
- 설치가 없어도 앱은 빌드·실행되고, 모든 팩이 대체 포장으로 표시된다.
- 설치 단계는 파일을 임시 이름으로 쓰고 다시 읽어 검증한 뒤에만 교체한다. 실패한 새 파일이 정상 파일을 덮어쓰지 않는다.
- `--write-manifest`는 항목 수가 줄어드는 쓰기를 거부한다.

## 3. 등록된 이미지

공개판 레지스트리는 비어 있다. 쓸 권리가 있는 이미지를 위 형식으로 등록하고 `./scripts/fetch-pack-artwork.sh --write-manifest`로 설치·검사한다.

## 4. 화면 표시 규칙

| 상태 | 표시 |
|---|---|
| 실물 포장 설치됨 | 실제 포장 그림. 표면에 디버그·대체 라벨을 붙이지 않는다 |
| 미설치 / 판본 불일치 / 파일 읽기 실패 | 대체 포장(세트 로고 + "PackTrace 대체 포장 / 실제 부스터 포장지가 아닙니다") |
| 출처·권리·설치 상태 | 설정 화면의 "팩 포장 이미지" 항목에서 읽을 수 있다 (팩 표면에 덮지 않는다) |

표시 상태는 `PackArtworkResolution`(`real` / `substitute(reason)`) 하나로 결정되며, 상점·보관함·받은 팩 화면·
개봉 장면이 모두 같은 매핑(`AppEnvironment.packArtwork(for:)`)을 쓴다.

## 5. 뜯기 연출에서의 분할

- 팩 프레임은 300×430pt, 절취선은 높이의 **21.4%**(= 92pt) 지점이다(`PackWrapFrame`).
- 그림은 프레임 안에 **비율을 유지한 채** 맞춰 넣고 가로 중앙 정렬한다(491×900 → 235×430). 늘리지 않는다.
- 상단 조각과 본체는 **같은 그림, 같은 배치**를 서로 다른 창(window)으로 잘라낸 것이다
  (`PackArtworkGeometry.stripWindow` / `bodyWindow`). 그래서 두 조각의 배율이 항상 같고 인쇄가 이어진다.
- 절취선은 그림 높이 기준 비율로 계산하므로 창 크기가 달라져도 같은 인쇄 위치에서 잘린다.
- 상단 조각에만 이동·회전·분리 변환을 적용하고, 본체에는 기존 장력·압축·추종을 유지한다.
- 그림이 없으면 같은 창 구조에 대체 포장(포일 그라디언트)을 그린다. 조작·임계점·저장 순서는 동일하다.
- M5.1에서 넣은 포일 반사·드리프트는 **대체 포장에만** 적용한다(실물 인쇄에 이미 있는 반사광과 겹치지 않게).

## 6. 이미지 파이프라인

M5.1의 `ImageCache`를 그대로 쓴다. 카드용 URL 규칙과 별개로 `ImageRequest`가 두 종류의 출처를 가진다.

| 항목 | 카드·세트 아트 | 설치된 포장 아트 |
|---|---|---|
| 출처 | `.remote(urlString)` | `.localFile(url, contentVersion)` |
| 캐시 키 | `sha256("<quality>\|<url>")` | `sha256("pack-art-<size>\|<path>\|<version>\|<해시 앞16>")` |
| 크기 | `low` 337px · `high` 825px | `tile` 480px · `opening` 900px |
| 네트워크 | 필요 | **없음** (파일을 그 자리에서 읽는다) |
| 실패 시 | 파일 삭제 후 1회 재다운로드 | 파일을 지우지 않는다. 대체 포장으로 표시하고 재시도 제공 |

디코딩은 액터 안에서 ImageIO로 하고 결과를 LRU(240)에 담는다. 파일 크기 상한(`maxInstalledBytes` 12MB)을 넘는
파일은 읽지 않는다. 같은 그림을 여러 화면이 동시에 요청하면 한 번만 읽는다.

## 7. 확인하지 못한 것

1. **아트워크 사용 권리** — 공개 라이선스 표기 없음. 비공개 개인용으로만 사용한다.
2. **인쇄 차수·지역 인쇄소** — 어느 판본의 인쇄인지 특정하지 못했다.
3. **등록한 아트가 세트의 대표 변형인지** — 위키 인포박스 지정을 따랐을 뿐, 제조사가 "대표"라고 발표한 자료는 확인하지 못했다.
4. **뒷면 이미지** — 확보하지 않았다. 360도 감상(후속 작업)에서도 뒷면을 검증된 인쇄면처럼 표시하지 않는다.
5. **나머지 부스터 아트 변형** — 존재만 확인하고 등록하지 않았다.
6. **사람의 손맛 평가** — 자동 검증만 수행했고 사람이 직접 뜯어본 평가는 하지 않았다.
